A practical guide you can come back to

Working with Copilot
in VS Code

We now have GitHub Copilot. Most of us have used a chat like ChatGPT, but not an AI that reads our code and edits files. This is how it works, how to get useful results out of it, and what to do when it gets things wrong.

It's not magic Context is your job Always verify
01 What Copilot actually is

A model that predicts the next words — from its training, plus whatever you put in front of it.

It does not know your project. It only knows what is in its context window — the text you show it right now. That single fact explains almost everything else in this talk.

SO IT'S GENUINELY USEFUL
Fast at reading code, drafting, explaining, and doing well-defined work — when you give it the right context.
SO BE CAREFUL
It can be confidently wrong and never says “I don't know.” Not an oracle. Not a search engine. And each new chat starts completely fresh — it has no memory between sessions.
Don't expect a perfect answer in one shot. Expect a fast draft you steer and check. Session amnesia is why saving context to a file matters.
02 The words you'll keep hearing

Seven words, in plain language.

ModelThe AI itself. Bigger, smarter models cost more and have lower limits.
Reasoning levelHow much it “thinks” before answering. Higher = better but slower and pricier.
Context windowIts working memory: everything it can see at once. It is limited — and it forgets the rest.
AgentThe mode where it can read files, run tools, and edit code in a loop — not just chat back.
Tool callWhen it runs something — search, read a file, run a test — to get info or make a change.
SkillA reusable text file of instructions for a task. Just text — more on this later.
MCPA standard way to plug it into outside tools and data. You decide if it asks before each action.
chat vs agentChat answers you. An agent goes and does — reading, running, editing — then reports back.
WHERE IT LIVESOpen Copilot Chat in the VS Code sidebar. A dropdown switches Ask / Edit / Agent mode; the model picker sits at the bottom of the chat box.
03 The models we have — and when to use which

Not all models are the same. The gap is huge.

The picker shows several models. The smart one is slow and expensive with low limits. The cheap ones are fast but weak. Pick deliberately.

The strong model
GPT‑5.3, high / extra‑high reasoning
Genuinely good at hard thinking. Expensive, slower, low limits. Save it for the parts that need a brain.
The cheap models
GPT‑5 mini, GPT‑4o
Fast and cheap. Fine for small, well-defined steps. Weak at anything complex — expect mistakes.
THE RULE Think hard with the expensive model — build the context and the plan. Then do the typing with a cheaper model that just follows it. Switch any time in the chat's model picker — hand the plan over in context.md.
Privacy: your prompts and the code you show it are sent to the model's API. Keep credentials, personal data, and internal secrets out of prompts.
04 The five levels of AI coding
Dan Shapiro

From typing faster → to changing the software process itself.

0 Spicy autocomplete Tab completion, snippets, regex help — AI as a faster keyboard
1 Coding intern “Write a unit test”, “add docs”, “convert this function” — isolated tasks
2 Junior developer Pairing inside the IDE; you inspect every line it writes
3 Developer AI writes most code; your job becomes diff, test, review
4 Engineering team You write specs and plans; agents execute bigger chunks
5 Dark software factory Specs go in, software comes out; humans mostly design the system
aim here now If you're just starting, you're at Level 0–1 today — that's fine. Aim for Level 2 → 3 for daily work. Level 5 is not the goal.
05 How it reads your code

It doesn't “know” your repo. It runs ordinary commands to look around.

The same things you'd do in a terminal — search, open a file, find usages. Nothing magic underneath.

$ grep -rn "calculateTotal" src/
$ read checkout.service.ts :40–90
$ find references validateAddress()
$ open reports/export.ts
It can miss files
If it never searches for the right thing, it never sees that code.
It can pollute its context
Reading lots of irrelevant files fills the window with noise.
So your job
Point it at the right files, and check what it actually looked at.
06 A workflow that works

Six steps, every time. Each has a job, an owner, and words to say.

1
Build context
YOU + STRONG MODEL
The story, the acceptance criteria, the files (#file, @workspace), the rules and skills to follow. Full recipe on the next slide.
“Here's the ticket + acceptance criteria. Don't edit anything yet.”
2
Make a plan
STRONG MODEL, HIGH REASONING
Still no code. It writes numbered steps plus the gathered context into context.md — the handoff file between chats, models, and teammates.
“Scan the repo, then write the context + step-by-step plan to context.md.”
3
Review the plan
YOU — NO MODEL
Read it like a PR: right files? right order? missing edge cases? Fixing a sentence here is far cheaper than fixing code later.
Your checklist: files · order · edge cases · what it didn't look at
4
Implement
CHEAP MODEL IS FINE
One plan step at a time. Edits arrive in a diff view — accept or reject per file. Following a good plan doesn't need a smart model.
“Do step 1 of context.md only. Stop after, before step 2.”
5
Verify
YOU + THE AGENT
Run it, test it, check it against the acceptance criteria — and check the layers agree: UI ↔ API ↔ DB. Never take “done” at its word.
“Verify step 1 against the acceptance criteria. Show me the evidence.”
6
Iterate
YOU STEER
Name the exact step that's wrong — not “it doesn't work.” If the chat has gone long or stubborn: fresh chat, paste context.md, continue.
“Step 3 is wrong: X happens instead of Y. Fix only step 3.”
THE SPLIT Steps 1–3 are thinking — spend the strong model there. Steps 4–6 are doing and checking — a cheap model can follow a good plan. context.md carries the work between them.
07 Building context, step by step

Step 1 of the workflow, in detail. This is most of the job.

1
Describe the task
Paste the story and the acceptance criteria — what “done” means.
“Here's the ticket + acceptance criteria…”
2
Point it at the code
Name where to start. Ask it to scan the repo and gather the related functions.
“Start in reports/. Find existing exports.”
3
Add the rules and references
Relevant skills, docs, links, examples to follow.
“Follow skills/write-tests.md and this doc.”
4
Write it down
Have it summarize the context and plan into a markdown file.
“Write the context + plan to context.md.”
5
Iterate and verify
Correct what's wrong, keep the file current, reuse it across chats.
“Update context.md with what we learned.”
HOW TO POINTType #file to attach a specific file, @workspace to let it search the whole repo — or just drag a file into the chat.
08 Prompts in practice

The strong prompt is just the workflow, written out.

WEAK
Add CSV export to the reports page.
STRONG — build context + plan first
Here's the story and acceptance criteria: <paste>. Start in reports/ and find how existing exports work. Don't edit yet — scan the repo, then write the context and a step-by-step plan to context.md.
WEAK
Does this work?
STRONG — verify against reality
Verify this change against the acceptance criteria. Check the UI calls match the backend API, and the API fields match the DB schema. List anything that doesn't line up.
09 What to actually ask it to do

Concrete asks you can copy today.

test“Write unit tests for this function — cover null, zero, and negative.”
verify“Walk through this feature end to end and tell me where it breaks.”
cross-check“Check the UI contract matches the backend, and the backend matches the DB.”
acceptance“Verify this change against the acceptance criteria in the story.”
ground“Use this file / link as the source of truth: <paste>.”
Notice the pattern: give it something real to check against — criteria, a contract, a link — not just “is this good?”
10 What a skill really is

A skill is just text. There's no magic in it.

.github/skills/write-unit-tests/SKILL.md
---
name: write-unit-tests
description: How we write unit
  tests. Use when adding tests.
---
When asked to add tests:
- use the framework in package.json
- mirror the nearest *.test.ts
- cover null, zero, negative cases
- don't change prod code unless a
  test reveals a real bug
It's just instructions
Almost the same as pasting them into the prompt yourself.
No special command needed
You can just say: “read skills/… and follow it.”
Write once, reuse
The format is an open standard — the same file works in Claude Code, Cursor, and other agents.
11 Creating your own skill

One file: SKILL.md — a small header, then plain instructions.

1
Pick a task you repeat
Write tests, review a PR, debug failing CI.
2
Write it like a teammate brief
Steps, rules, examples, what a good result looks like.
3
Save as SKILL.md
Project: .github/skills/<name>/ · personal: ~/.copilot/skills/
4
Use it, then refine
Copilot picks it up from the description, or type /skill-name in chat. Update it when it misses.
SKILL.MD FORMAT
---
name: review-pr
description: What it does, and
  when Copilot should use it
---
# Instructions
Steps, rules, examples — plain
markdown, written like a brief
name + description are required;
the body is free-form text
Skill vs. custom instructions: a skill is pulled in for a specific task; custom instructions are always-on rules for the whole repo. Type /skills in chat to see and manage what's installed.
12 When the model gets it wrong

It will be dumb sometimes. That's normal — here's how to handle it.

SET YOUR EXPECTATIONS
Cheap models will get things wrong. That's expected, not your fault.
So spend the expensive, high-reasoning model where it counts: context and the plan. Let a cheap model do the typing.
It can also invent things — library names, methods, imports that don't exist. Check imports against the real package docs.
DROP TO A LOWER LEVEL
Don't ask for a whole feature. Drive it one small step at a time:
1. Create this one component / service
2. Now create the next one
3. Now connect them
4. Now write tests for them
5. Now extend it a little further
The harder the task — or the weaker the model — the smaller the steps.
FIRST MOVEDon't argue with a bad answer — reject the changes, open a fresh chat, paste context.md. Long chats degrade: keep it to one task per chat.
